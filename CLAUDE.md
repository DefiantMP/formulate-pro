# Formulate Pro — Project Memory

Tablet formulation calculator for nutraceutical manufacturing. Used by operators making products and by client companies requesting them. Next.js 14 App Router + TypeScript, rebuilt from an HTML prototype to add real reactive state and AI-assisted verification.

## Open Flags / Watch Items

Known gaps and traps, deliberately at the top of this file so they're in view before any work starts. These are *not* the same as the Outstanding Items checklist at the bottom — that tracks features still to build; this tracks things that will bite silently if forgotten. Added 2026-08-13 with the component spec / lot traceability system.

- **`GET /api/lots` now computes `specStatus` (2026-09-04).** It previously omitted it, which blocked the run lot-picker. Resolved with ONE batched query reusing `lotSpecStatusInclude` and the same `lotSpecStatus` rollup the detail endpoint uses — deliberately NOT a denormalized cached column, which would need invalidating on every spec revision, test and OOS approval, and whose every missed invalidation shows up as a lot reporting the wrong QC verdict. `specTests` are dropped from the list payload after the verdict is computed, so the response stays small. The material detail page's lot list now shows the badge (its old "status deliberately absent" note is gone). List and detail verdicts were cross-checked across pass/fail/pending and agree; if you ever make them diverge, that is a bug, not an optimization.
- **`resolveLatestTests` (`lib/lotSpecStatus.ts`) is DISPLAY-ONLY.** It answers "what's the current result for this parameter" by recency, and deliberately disagrees with the status rollup, which treats failures as sticky (see invariants below). A pinning test in `lib/lotSpecStatus.test.ts` asserts the two diverge, specifically so nobody later "fixes" the rollup back to recency-wins. **No UI surface may render a lot-level pass/fail from it** — parameter-level display only. Rendering a lot verdict from the latest test reintroduces retest laundering in the presentation layer, where it's harder to spot than it would have been in the rollup.
- **`parseSpecCriterion` (`lib/rawMaterials.ts`) has been covered by `lib/rawMaterials.test.ts` since 2026-09-17**, along with the category/source-type/test-type guards and `toSpecTestInputs`. Two gaps are pinned as *current behaviour*, not endorsed: a `targetValue` outside its own min/max is accepted, and a qualitative criterion with no `passCriteriaText` is accepted (stored as null — a pass condition nobody wrote down). Tightening either is a QC decision for whoever owns the specs; changing it means updating the pinning test deliberately.
- **Naming collision on `actualMgPerTablet`.** Two unrelated fields share the name: `RegrindResult.actualMgPerTablet` (`lib/calc-engine/types.ts`) is a *calculated* figure — the actual dose after rounding to whole tablets — while `Run.actualMgPerTablet` (`prisma/schema.prisma`) is a *lab-measured* COA result entered after the batch is made. Never reference "actualMgPerTablet" in code, comments, prompts, or conversation without qualifying which one. A variance calculation that crosses them silently compares a rounding artifact against an assay result.
- **`getRunIngredientBreakdown` collapses all regrind lots into one aggregate "Reground powder" row** (`lib/runIngredientBreakdown.ts`), so per-lot scale verification is impossible today — an operator can only verify the combined powder weight, not each lot. Making per-lot verification work requires changing both that function *and* the `ingredientLabel`-as-plain-string design in `ScaleVerification` (a string match against synthesized breakdown labels, with no stable per-ingredient id to key on). Neither change is small; don't promise per-lot verification without accounting for both.
- **The run lot-picker exists (2026-09-04)** — `RunLotPicker` on the New run page, sending `lotUsages` on save. It shows each lot's QC status from the server rollup but deliberately does NOT hide or disable a failing/untested lot: with GMP mode off consuming one is legitimate, and with it on the server decides warn vs block. Hiding it would make the picker quietly disagree with the setting.
- **GMP Mode (2026-09-02) is now fully wired (2026-09-04).** The toggle, append-only audit log, batch review, two-person weighing, deviations and identity-spec surfacing all ship — and both gates that were previously unreachable now fire at run save: a material with no active qualitative identity criterion is refused, and a lot whose `specStatus` is fail/pending warns or blocks per `GmpSettings.lotStatusEnforcement`. Rules live in `lib/gmp.ts` and `lib/runLotUsage.ts`, both pure and tested.
- **Stock corrections are append-only (2026-09-04).** `LotAdjustment` records a signed `deltaG` with a reason; `POST /api/lots/[id]/adjustments` writes the row and moves `Lot.quantityRemainingG` in one transaction. There is deliberately no PATCH or DELETE: a wrong adjustment is corrected by another in the opposite direction, so the history shows what was believed and when it changed. Making the row editable would restore the silent-quantity problem it exists to fix. Consuming more than remains, or adjusting below zero, is refused regardless of GMP mode — arithmetic, not policy. `Lot.quantityRemainingG` is still the stored running figure rather than a derived sum, so every existing read path is unchanged.
- **`fmt()` clamps anything <= 0 to `'0'`.** Correct for weights, which cannot be negative, and load-bearing wherever an unset field must not read as a real figure — but it silently rendered a `-50g` stock adjustment as `"0 g"`. Use `fmtSigned()` for any value that can legitimately be negative. Pinned by a test in `lib/format.test.ts` that asserts both behaviours.

### Spec System Invariants — do not "optimize" these away

These are deliberate, load-bearing decisions in `lib/lotSpecStatus.ts` and the `/api/raw-materials`, `/api/lots`, `/api/oos-investigations` routes. Each one looks like a bug or an inefficiency from the outside; each is covered by tests. Changing any of them is a QA-integrity decision, not a refactor.

- **Failures are sticky.** Once any `LotSpecTest` for a criterion has `passFail: false`, that criterion — and so the lot — stays `fail`. A later passing retest does **not** supersede it. Retesting until the answer is acceptable is precisely what the OOS record exists to prevent, so the burden is on the investigation, not on recency.
- **Only an approved `OosInvestigation` with `disposition: 'invalidate_original_result'` can clear a failure**, and only when *both* `approvedBy` and `approvedAt` are set (`isInvalidatingInvestigation`). `confirm_original_result` and `reject_lot` never clear anything, and an unapproved investigation carries no weight regardless of its disposition. Approval stamps `approvedAt` server-side in the same write as `approvedBy` so the two can never be set independently.
- **Invalidation is scoped to the single test it names**, never to the criterion. A *new* failure after an invalidated one still fails — an invalidation is not a forward-looking waiver.
- **An empty or absent spec is `pending`, never `pass`.** "Every criterion passed" is vacuously true with zero criteria, and reporting a never-tested lot as released is the exact failure mode the system exists to prevent.
- **An invalidated failure with no later passing test is `pending`, never `pass`.** Setting a bad result aside doesn't demonstrate conformance; something still has to affirmatively pass.
- **Numeric `passFail` is computed server-side** by `evaluateNumericResult` against the criterion's own min/max, and any client-supplied `passFail` on a `numeric_range` criterion is ignored outright — the same "code computes the verdict, the client doesn't assert it" split as the AI Verification integrity gate and `ScaleVerification`'s pass/fail. Only qualitative criteria accept an operator-set verdict, and there it's required rather than defaulted, so an omitted verdict can't record as a pass.
- **`SpecCriterion` is soft-deleted via `retiredAt`, never hard-deleted.** `LotSpecTest`'s FK to it is `RESTRICT`, so a real delete would either be blocked or would take the historical results with it. Retiring drops the criterion out of the active spec (and therefore out of status, since the rollup only considers criteria currently on the spec) while every test row survives. This is why `lotSpecStatusInclude` filters `criteria` to `retiredAt: null` — that filter is load-bearing, not cosmetic: without it a retired criterion still holds lots at `pending` or `fail`.

## Auth & GMP Mode — read before touching either

Added 2026-09-02. Both are load-bearing for compliance behavior.

- **`lib/gmp.ts` holds every enforcement rule as a pure function** — DB-free, like `lib/lotSpecStatus.ts`, so a compliance reviewer can read the rules without reading route handlers. Enforcement is gated on GMP mode; **display never is**. Gating visibility on a settings flag would make history depend on current configuration, which is the opposite of auditable. Do not add a rule that hides records when the mode is off.
- **Grandfathering is derived, not stored.** `gmpFirstEnabledAt` reads the earliest `GmpModeToggleLog` row with `newState: true`. There is deliberately no `gmpFirstEnabledAt` column, because a stored summary could disagree with the log it summarises — and the log is the compliance artifact. A record created before that moment is never flagged: it was made under rules that did not exist.
- **`GmpModeToggleLog` is append-only.** No endpoint updates or deletes it. The toggle itself is deliberately *not* locked — a lock that can be lifted proves nothing, while a complete record of who changed what and when does.
- **Two-person weighing compares ACCOUNT IDS, never names.** The original version compared strings, which let one person satisfy the check by typing two names. Verification is a step-up credential check: the verifier supplies their own email and password on the verify action (`PATCH /api/scale-verifications/[id]`), validated server-side, and the resulting id must differ from the weigher's. A full session swap was rejected as impractical mid-batch on a shared terminal; a name dropdown would restore the original loophole. **Do not replace this with a picker.**
- **Signup never grants a role.** A signup becomes `admin` only when **no active admin exists**; every other one is an `operator`. Promotion is admin-only via `PATCH /api/users/[id]`. Letting signup choose meant anyone reachable could sign off their own batches. The bootstrap originally counted *every* user including deactivated ones, which left an instance whose only accounts were non-admins with no way to ever get an admin (the real state of dev.db until 2026-09-17). Counting active admins is safe only because the last active admin can be neither demoted nor deactivated (`wouldRemoveLastAdmin`, `lib/auth.ts`) — keep that guard, or the bootstrap becomes a way to mint an admin.
- **Accounts are deactivated, never deleted (2026-09-17).** `DELETE /api/users/[id]` sets `deletedAt`, and `POST /api/users/[id]/reactivate` clears it — restoring the old role, but leaving `sessionsValidFrom` so pre-deactivation sessions stay ended. Signed-in users change their own password (current password required, shares the sign-in throttle) and sign out everywhere from Settings → Your account; an account is referenced by every batch, weighing and GMP log entry it signed. **Never hard-delete a `User` row by hand either**: on 2026-09-04 a test account was deleted directly with sqlite after it had toggled GMP mode, leaving that `GmpModeToggleLog` row pointing at nothing (`PRAGMA foreign_key_check` reports it). The row was deliberately not edited — the log is append-only — and the log UI labels it "Account no longer exists" via `gmpActorLabel` (`lib/gmp.ts`).
- **Password reset is admin-issued (2026-09-17)** — no email in this app. An admin generates a one-time link from Settings → Accounts (`POST /api/users/[id]/reset-link`); it expires in 1 hour, only its SHA-256 is stored, issuing another revokes the older one, and using it (`/reset-password`) is claimed conditionally inside the transaction so two submits cannot both succeed. `PasswordResetToken` rows are kept after use as the record of who reset whose password.
- **Resetting or changing a password, "sign out everywhere", and deactivation all end that account's existing sessions**, via `User.sessionsValidFrom` checked in `getCurrentUser` (`sessionStillValid`). It is compared against the token's **original sign-in time `authAtMs`, never `iat`**: middleware renews sessions without reading the DB, so a cut-off session still gets a fresh `iat`, and comparing against that would resurrect it. `authAtMs` is milliseconds because a whole-second comparison let a session signed in during the same second as "sign out everywhere" survive it (caught in live testing 2026-09-17). A password change keeps its own session by issuing a new token whose `authAtMs` is at or after the cut-off.
- **Sessions time out after 1 hour idle and 8 hours absolute (2026-09-17)** — `lib/sessionToken.ts`, deliberately bcrypt-free so `middleware.ts` (edge) can import it. Middleware re-issues the cookie once it is 5+ minutes old, carrying `authAtMs` forward unchanged so activity can never extend past 8 hours from sign-in. It skips `/api/auth/*`, which set or clear the cookie themselves. The idle window is an hour rather than less so an operator is not signed out during a 20-minute main mix. Middleware never decides who is signed in — `getCurrentUser` still does, from the DB.
- **Forgotten passwords are recovered with a one-time recovery code (2026-09-17)** — `lib/recoveryCode.ts`. App-generated (16 chars, 80 bits, alphabet without I/O/0/1), shown once at signup behind an "I have saved this" checkbox, stored only as a bcrypt hash in `User.recoveryCodeHash`. "Forgot password?" on the sign-in page takes email + code + new password (`POST /api/auth/recover`): shares the sign-in throttle, one message for unknown email vs wrong code, spends and **replaces** the code (claimed conditionally on the old hash so two uses cannot both win), ends every session and signs this one in. Settings → Your account creates/replaces a code (current password required) and nags accounts made before codes existed. Email reset links were deliberately deferred — the app sends no email; add them when remote sign-in arrives. **Last resort**, for a lost code with no admin able to help: `npm run reset-password -- <email>` on the host sets a printed temporary password and ends sessions; it needs no password because anyone who can run it can already edit the database, and it never reactivates an account or changes a role.
- **Every credential check runs bcrypt even when the account does not exist** (`verifyOrDummy`, `lib/auth.ts`). Sign-in used to skip bcrypt for unknown emails and answered in ~4 ms vs ~250 ms, which revealed which emails had accounts despite the identical error message. Use `verifyOrDummy` for any new check keyed by a typed email.
- **Sign-in is throttled by the typed email, not the account** (`lib/loginThrottle.ts`, `LoginThrottle` table): 5 failures in 15 minutes locks that email for 15 minutes, checked before the password is verified. Keying by email makes an unknown address lock identically to a real one, so the lock message cannot be used to discover who has an account. DB-backed because the dev server restarts constantly and an in-memory counter would silently reset. A successful sign-in or a reset clears it.
- **Legacy free-text identity is preserved via `@map`.** `Run.legacyReviewerName`, `ScaleVerification.legacyWeighedByName`/`legacyVerifiedByName`, `RunDeviation.legacyOpenedBy`/`legacyClosedBy`, `GmpModeToggleLog.legacyActorName` all keep their original columns — the rename cost no data movement. They are **never** auto-matched to accounts by name similarity: guessing which account an old string meant would put a signature on a batch record nobody gave.
- **`AUTH_SECRET` is required** and short/missing secrets throw rather than falling back to a default, which would make every deployment's cookies forgeable by anyone who can read the repo. It lives in `.env.local` (gitignored).
- **With GMP mode off there is NO access control at all** — every route is reachable signed out. Deliberate, consistent with "mode off is permissive", and fine for a local single-company tool. Revisit before any network exposure.

## Domain Rules — Ingredient Architecture

- A formulation is a list of ingredients. Exactly one ingredient has role `"calculatedByDifference"` (the filler — Emdex or Dipac, an extensible list via `FRESH_FILLER_TYPES` in `lib/calc-engine/types.ts`, 1:1 interchangeable with no calc impact). All other ingredients carry fixed percentages. Active ingredients are a separate concept from this list — see the fresh-batch multi-API note below; regrind mode still keeps a single default `role: "active"` ingredient in `defaultIngredients()` for its own display purposes only.
- The architecture must support any number of ingredients, not just the original 4-ingredient default. Real production formulations (e.g. RR77-PB9) use 5+ ingredients.
- Fresh-batch mode vs. regrind mode use different math — this distinction caused a real production-blocking bug once already:
  - **Regrind mode:** raw material potency percentage = the active ingredient's percentage of the blend directly.
  - **Fresh-batch mode:** blend percentage must be derived from potency + target mg/tablet + target tablet weight. It is NOT the same as raw potency percentage. Any change to fresh-batch calculation must be validated against a known-correct production sheet before being trusted.
- Known-good validation case (RR77-PB9, default 5-ingredient formulation — PVPP XL 5%, Magnesium stearate 2%, EZTAB 10% — at potency 76.4%, target 60mg/tablet, target weight 0.69g, 10,887 tablets): 855.00g active, 5,379.98g Emdex, 375.60g PVPP XL, 150.24g Magnesium stearate, 751.20g EZTAB, total 7,512.03g. Verified directly against `calculateFreshBatch` on 2026-07-13 and matches `lib/calc-engine/tests/calcEngine.test.ts`. (An earlier version of this note had different Emdex/PVPP XL/Magnesium stearate figures — those were wrong, presumably transcribed from a formulation with different excipient percentages; corrected here.) Use this to sanity-check any engine changes.
- **Fresh-batch single-API math validated against the operator's own Tabulator workbook (2026-09-18).** "7Ω Tabulator RR Formulations.xlsx" — a separate spreadsheet tool the operator used before this app, one formulation per tab, 47 non-empty tabs dated Oct 2024 – Jul 2026 across three template versions. Every tab was read generically (column B labels / column C values, using the cells' cached results; the filler is the one `%` row computed as `MINUS(100%, …)`) and run through `calculateFreshBatch`. **All 43 tabs that record gram amounts match to 0.000 g on every ingredient and the total**; the 4 earliest tabs (V1, V2 and two copies) record no grams but their totals match. This is independent evidence — nothing in that workbook was calculated by this app — unlike the regrind history, which was. The RR77-PB9 tab is the CURRENT version of the reference case below: PVPP XL 4% and Magnesium stearate 1% (its own notes record the change from 5% and 2%), giving Emdex 5,530.23 g, PVPP 300.48 g, Mag 75.12 g, EZTAB 751.20 g, total 7,512.03 g. The workbook's "tablets manufacturable from available stock" cells also match `solveFreshBatchMaxTablets` (855 g → 10,887; 8,000 g → 480,571 on the separate OG sheet PB56 EZT). Still not validated: multi-API combos and regrind — the workbook holds neither.
- Regrind mode has a real-formulation validation pass still pending (waiting on a colleague's regrind sheet) — treat regrind math as less battle-tested than fresh-batch until that lands.
- Regrind mode supports multiple lots per run (`RegrindLot[]` in `lib/calc-engine/types.ts`): each lot has its own potency, pressed weight, and powder weight; `calculateRegrind` blends `activeInOldPowderG` as the sum of each lot's `weightG × effectivePotency`, divided by the operator-entered `regroundPowderG` (which stays authoritative for all downstream math — the lot-weight sum only drives a mismatch warning, never overrides it). Single-lot behavior is proven byte-for-byte identical to the pre-multi-lot formula by regression tests in `calcEngine.test.ts` against the original golden fixtures. This blended math is new and, like single-lot regrind above, has not yet been validated against a real (ideally multi-lot) production sheet — added 2026-07-14, still pending that validation.
- Fresh-batch mode supports multiple APIs per run (combo products, `apis: FreshApiEntry[]` in `lib/calc-engine/types.ts`, replacing the old single `targetActiveMgPerTablet`/`potencyPercent` scalars): each API has its own label, target mg/tablet, and potency, dosed independently. The potency *method* (bulk % vs mg-per-unit) is a single choice shared across every API in a run — enforced by the UI, not the type. `calculateFreshBatch` computes each API's own raw-material % of blend exactly like the original single-active formula, then sums those percents for the combined `activePercentOfBlend`; filler math subtracts that combined total (plus fixed excipients) from 100%, same structure as before. `ingredients` passed to `calculateFreshBatch` must no longer contain any `role: "active"` entry — actives come entirely from `apis[]` now (regrind's own `defaultIngredients()` active entry is untouched). Single-API behavior is proven byte-for-byte identical to the pre-combo-product formula by regression tests in `calcEngine.test.ts` against the RR77-PB9 golden fixture above — added 2026-07-15.
- Regrind mode has a "solve for target tablet count" mode (`solveRegrindLotWeight` in `lib/calc-engine/calcEngine.ts`): given a target tablet count and exactly one lot marked as unknown, it solves for that lot's required weight, deliberately as a fully separate, standalone calculation from `calculateRegrind` — it does not modify that function at all. The caller (UI) feeds the solved weight back into an ordinary lot and calls the unmodified `calculateRegrind` with `regroundPowderG` set to the full lot-weight sum, reusing the exact same battle-tested math for the per-lot breakdown, filler, and totals rather than duplicating it. Default (non-solve) regrind behavior is therefore untouched by construction, not just by test coverage. Verified against a known-correct worked example (Lot 1 fixed 11,346.14g @ 14/730 potency, Lot 2 solved @ 40/690 potency, target 100,000 tablets/14mg/0.8g): filler matches the reference figure (48,257.4g) exactly; the solved lot weight computes to 20,396.45g, ~0.05g off the reference figure (20,396.5g) — a rounding artifact in how that reference number was manually derived, not a formula error (see `calcEngine.test.ts` comment). Added 2026-07-16, not yet validated against a real production sheet.
- Regrind mode adds a fresh lubricant top-up (`REGRIND_LUBRICANT_TOPUP_PERCENT` in `lib/calc-engine/calcEngine.ts`, currently 0.15% — changed down from 1% on 2026-07-20, e.g. Magnesium stearate), restricted to lots marked `sourceType: 'regroundTablets'` (`RegrindLotSourceType` in `lib/calc-engine/types.ts`) — raw/bulk powder lots (`sourceType: 'rawPowder'`, never previously pressed) contribute nothing. Formula: `tabletCount × targetWeightG × 0.0015 × (reground-tablet lot weight ÷ total lot weight)`, redistributed out of `fillerAddG` rather than added on top (`totalBlendG` is unaffected regardless of the lot mix). `sourceType` defaults to `'regroundTablets'` for every new lot and for lots restored from runs saved before this field existed, so a 100%-reground-tablets batch — the common case, and every pre-existing saved run — reduces to exactly the same top-up as before this restriction (fraction = 1); an all-raw-powder batch gets a top-up of exactly 0, and the "already present, add only the top-up" row/warning/SOP-step are all omitted entirely in that case rather than showing a 0g line. This deliberately coexists with the "already present, don't add fresh" assumption for that same ingredient elsewhere — most of it is still assumed already in the reground powder, this is a small controlled top-up, not a full fresh addition. The lubricant ingredient was removed from `alreadyPresentIngredientNames` (which now covers disintegrant only) and is instead threaded through as its own `lubricantTopUpIngredientName` field. `solveRegrindLotWeight`'s own feasibility check independently applies the same source-type-scaled formula to its `fillerAddG`, so it stays consistent with what `calculateRegrind` will actually compute once the solved lot is fed back in — proven by a test that feeds a solved lot into `calculateRegrind` and checks the two `fillerAddG` figures match exactly. Added 2026-07-16 (top-up), restricted to reground-tablet lots 2026-07-17, percentage reduced to 0.15% 2026-07-20, not yet validated against a real production sheet — this is a deliberate change to default regrind math (not additive/opt-in), so treat it with the same caution as any other regrind formula change.
- Regrind mode also adds two fixed processing aids to help with pressing, EasyTab and Silicon Dioxide, each `REGRIND_EASYTAB_PERCENT` / `REGRIND_SILICON_DIOXIDE_PERCENT` (0.15% of `totalBlendG`) in `lib/calc-engine/calcEngine.ts` — carved out of filler the same way as the lubricant top-up, but NOT scoped to `sourceType: 'regroundTablets'`; they apply uniformly regardless of lot mix, since they're standard processing aids added fresh every batch rather than something assumed already present from a prior press. Added 2026-07-20. As of the same date, regrind's calculated bulk filler (`fillerIngredientName` in `RegrindInput`) is hardcoded to `'EasyTab'` rather than sharing the fresh-batch Emdex/Dipac selector (`fillerIngredient` in `components/FormulateApp.tsx`) — the bulk filler amount and the fixed 0.15% EasyTab processing aid are the same physical material, so the UI/SOP merge them into a single "EasyTab to add" line (`result.fillerAddG + result.easyTabG`); `calculateRegrind`/`solveRegrindLotWeight` still compute the two amounts as separate result fields internally, the merge is display-layer only. Silicon Dioxide stays its own separate line. Fresh-batch mode's Emdex/Dipac filler selector is unaffected — this is a regrind-only divergence. Neither of these two processing aids nor this filler rename is yet validated against a real production sheet.
- Fresh-batch mode has a "solve for max tablets from available stock" mode (`solveFreshBatchMaxTablets` in `lib/calc-engine/calcEngine.ts`, input/result types `FreshApiStockEntry` / `FreshBatchSolveMaxInput` / `FreshBatchSolveMaxResult` in `types.ts`): given each API's available raw-material stock (g) instead of a manual tablet count, it computes `maxTabletsFromThisAPI = floor((availableStockG × potencyFraction) ÷ (targetActiveMgPerTablet / 1000))` per API, and the achievable tablet count is the minimum across all APIs (whichever API's stock runs out first constrains the batch) — that API is flagged as `isLimiting`. Same pattern as `solveRegrindLotWeight`: a fully separate, standalone calculation that never calls or modifies `calculateFreshBatch` — the caller feeds the solved `tabletCount` back into an ordinary `FreshBatchInput` (dropping `availableStockG`, which `calculateFreshBatch` has no use for) and calls the unmodified `calculateFreshBatch` to get the per-API grams, filler, and totals. Default (manual tablet-count) fresh-batch behavior is therefore untouched by construction, not just by test coverage. Tied directly to the RR77-PB9 golden fixture above: feeding 855.00g available stock back in solves for exactly 10,887 tablets, and re-running `calculateFreshBatch` with that solved count reproduces the golden totals exactly (see `calcEngine.test.ts`). Added 2026-07-21, not yet validated against a real multi-API production stock scenario.
- `activePercentOfBlendFromDose` (`lib/calc-engine/calcEngine.ts`, added 2026-07-22) is a small standalone export of the same mg/tablet → %-of-blend formula `calculateFreshBatch` uses internally (`targetActiveMgPerTablet / (bulkPotencyPercent/100)`, then that raw-material mg as a % of `tabletWeightG × 1000`) — parameterized on plain numbers (bulk % only, no `FreshApiPotency` union) so non-Fresh-Batch consumers (currently: the Formulations library builder, see below) can reuse the exact same derivation without needing a full `calculateFreshBatch` call. Does not call or modify `calculateFreshBatch`.

## Domain Rules — Raw Materials, Lots & Component Specs

Incoming-material traceability and QC, added 2026-08-13. Six models in `prisma/schema.prisma`, all new and purely additive — no existing table's columns were changed. This is a *records* system, not a calculation one: nothing here is wired into `calculateFreshBatch`/`calculateRegrind`.

Operator UI shipped 2026-08-16 (`/raw-materials`, `/raw-materials/[id]`, `/lots/[id]`, reached via the "Raw materials" sidebar entry). Components: `RawMaterialsPage`, `RawMaterialDetailPage`, `SpecEditor`, `ReceiveLotForm`, `LotDetailPage`, `LogSpecTestForm`, `OosInvestigationPanel`. Two rules the UI carries and that any change to it must preserve:

- **Lot-level pass/fail is rendered only from `LotDetailRecord.specStatus`** (the server rollup). `resolveLatestTests` drives the per-parameter "Current result" line and nothing else — see the DISPLAY-ONLY flag in Open Flags. The two are shown side by side deliberately: a lot whose latest purity result passes still reads FAIL while the earlier failure stands.
- **Approval is presented as terminal.** The approve control is disabled until root cause and a non-`pending` disposition exist, then requires a separate confirmation restating what that disposition will and won't do. `OOS_DISPOSITION_LABELS` / `OOS_DISPOSITION_EFFECTS` live in `lib/lotSpecStatus.ts` next to `isInvalidatingInvestigation` so the copy can't drift from the rule — edit them there, not in the component.

- **The model chain is `RawMaterial → Lot → LotSpecTest`, with the spec hanging off the material.** A `RawMaterial` is a material as a *kind* ("Magnesium stearate", unique by name, categorized active/filler/lubricant/glidant/disintegrant/other). A `Lot` is one physical receipt of that material — a lot number, a received quantity, a remaining quantity, and a `sourceType`. A `ComponentSpec` is the QC spec for a raw material (**exactly one per material**, enforced by `@unique` on the FK), holding `SpecCriterion` rows — one per testable parameter ("Identity", "Purity", "Contaminant — heavy metals"), each either `numeric_range` (min/max/target) or `qualitative` (free-text pass condition). A `LotSpecTest` is one criterion evaluated against one lot. An `OosInvestigation` is the formal record attached to a *specific failing* `LotSpecTest`, and is the only thing that can set that failure aside.
- **`Lot.sourceType` deliberately overlaps the calc engine but is not the same type.** `'regroundTablets'` and `'rawPowder'` align exactly with `RegrindLotSourceType` in `lib/calc-engine/types.ts` so a lot maps into a regrind run without translation; `'purchased'` is additional here and has no calc-engine meaning. Keep the two in sync if either grows.
- **Multiple tests per (lot, criterion) are expected, not a data error.** Retesting after an out-of-spec result is normal, so there is deliberately no unique constraint there. This is why the rollup can't just read "the" result for a parameter — see below.
- **The relational `Lot` data and the JSON lot data in `Run.inputs`/`Run.result` are separate on purpose and must stay that way.** The JSON is the calc engine's own input and output — potencies, weights, the numbers the math actually ran on — and remains the source of truth for the calculation; the calc engine never reads a `Lot` row. The `Lot` table answers the question that JSON can't: which received, QC'd, lot-numbered material physically went in. `RunLotUsage` is the join between them (`runId`, `lotId`, `amountUsedG`, `roleInRun` like `"regrind"` / `"fresh_filler"`). Do not "unify" these by having the calculator read lots, or by backfilling `Run.inputs` from `RunLotUsage` — a run's math must stay reproducible from its own stored inputs regardless of what later happens to inventory records. `RunLotUsage` rows are created server-side during run save only; there is intentionally no user-facing endpoint for them (and no run-save wiring yet, so none are ever created — see Outstanding Items).
- **Lot spec status is computed, never stored** (`lib/lotSpecStatus.ts`, surfaced by `GET /api/lots/[id]`). It derives from the material's *current* criteria plus every test and OOS investigation, all of which change independently of the lot; caching it would mean recomputing on every spec revision, test, and approval, with the usual drift risk. `computeLotSpecStatus` returns `'pass' | 'fail' | 'pending'`; `computeCriterionStatuses` gives the per-parameter breakdown behind that verdict. `lotSpecStatusInclude` is the exact Prisma `include` these need — use it rather than hand-rolling the query, since two parts of it are load-bearing (it pulls `oosInvestigations` alongside the tests, and filters `criteria` to `retiredAt: null`).
- **`resolveCriterionStatus` (the rollup) and `resolveLatestTests` (display) answer different questions and deliberately disagree.** The rollup scans a criterion's *whole* history and treats any failure as sticky; `resolveLatestTests` picks the newest test per criterion by `testedAt` (tie-broken by `createdAt`) and is only valid for showing "the current result for this parameter". Read the Spec System Invariants at the top of this file before touching either — the divergence is pinned by a test, and the rules about what clears a failure, what counts as pending, who computes `passFail`, and why `SpecCriterion` is soft-deleted rather than deleted all live there.
- **API surface** — conventions follow `app/api/runs/[id]/route.ts` (partial-update PATCH, `{ error }` bodies, 201 on create). `/api/raw-materials` (GET list with `?category`/`?q`, POST create), `/api/raw-materials/[id]` (GET with spec + active criteria + a separate `retiredCriteria` array, PATCH rename/recategorize), `/api/raw-materials/[id]/spec` (GET, **PUT** — full intended criteria list, idempotent; items with an `id` are edited, items without are created, and anything on the spec but absent from the payload is *retired*, all in one transaction), `/api/lots` (GET list/search with `?rawMaterialId`/`?sourceType`/`?q`, POST receive), `/api/lots/[id]` (GET, the only endpoint that computes `specStatus` — the list omits it, see Open Flags), `/api/lots/[id]/spec-tests` (POST log a result), `/api/oos-investigations` (GET list with `?lotId`/`?disposition`/`?open`, POST open), `/api/oos-investigations/[id]` (GET, PATCH work/approve). There is no lot PATCH and no delete endpoint anywhere in this system.
- **Write-time integrity checks that the schema can't express**, enforced in the routes: a `LotSpecTest` may only reference a criterion belonging to *that lot's material's* spec (otherwise the result files against a spec line the rollup will never read, and is silently never counted), and not a retired one; an `OosInvestigation` may only be opened against a test that actually **failed**, and its `lotId` must match the lot of its `failedLotSpecTestId` (both FKs are on the row, so they can disagree — a mismatch would file the case under a lot whose status it has no bearing on); approval requires a non-`pending` disposition and non-empty `rootCauseFindings`, stamps `approvedAt` server-side alongside `approvedBy`, and is terminal — an approved investigation is frozen, and reopening means opening a new one against the same failing test.

## Floating panels must not be clipped (2026-09-17)

- **Every popover renders through a portal at the page level** (`components/Popover.tsx`), never inside the card it belongs to. `.card` is `overflow: hidden` and `.col-left` is 270px, so a 290px confirm box positioned inside one was cut off at *every* window size — the operator saw a panel with its buttons sliced away. An ancestor with `overflow` anywhere up the tree clips absolutely-positioned children; the portal sidesteps the whole class of bug.
- **`lib/popoverPosition.ts` is pure and tested.** It shifts the panel sideways to stay on screen, flips it above the anchor when there is no room below, narrows it on a small window, caps its height so it scrolls its own content instead of losing its buttons, and — the regression that caught me — clamps it into the viewport even when the ANCHOR has been scrolled out of view, which happens because these controls sit inside scrolling columns.
- **A flex-centred overlay taller than its container cannot be scrolled to.** `.name-run-overlay` centred its card with `align-items: center`; in a 900x300 window the "Start run" button sat below the fold, unreachable. Fixed with `align-items: flex-start` + `margin: auto` on the card, which centres when there is room and scrolls when there is not. Use that pattern, not `align-items: center`, for anything that can outgrow its box.
- Verified live at 1024x768, 420x700, 280x260 and 900x300: panel fully on screen and every button reachable at each.

## Products pages (2026-09-17)

- **`/products` and `/products/[product]`** (`ProductsPage`, `ProductDetailPage`), reached from the sidebar's Products entry — the last inert nav button, now a real page. Both derive everything from run history via `summarizeProducts` / `summarizeProduct` in `lib/productHistory.ts`; there is still no Product table, for the same reason `/api/products` has none: a product is "something we have made batches of", so the runs ARE the list, and a separate record could drift out of step with them.
- **The typical recipe is medians with ranges, never means.** `summarizeFigure` returns median + min/max + `varies` (spread > `VARIES_THRESHOLD`, 10% of the median); the UI shows a single number only when the figure is settled and the range when it is not. Averaging 60mg and 14mg batches yields a dose nobody ever pressed — the same "no averaging across runs" rule `PriorRunsPanel` already states.
- **Only FRESH runs feed the recipe.** A regrind blend is mostly reworked material whose excipients came in with it, so folding its percentages in would describe a blend nobody weighed out. Regrind runs still count toward run totals and dates; a regrind-only product says it has no recipe rather than inventing one.
- **A run's name and product can be corrected from Run history** (`RunIdentityEditor`, 2026-09-18), with a "No product" filter listing the runs the Products page cannot see. It PATCHes only `label`/`product` — never inputs or results, so the batch's recorded numbers cannot change this way, and the PATCH carries no composition, so `syncFormulationFromRun` does not fire. Not locked on reviewed runs: name and product are filing metadata, not the batch record's figures.
- **Names are grouped case- and space-insensitively**, showing the most-used spelling (`groupByName`). Real data had one product's filler recorded as "EZTAB", "EZTab" and "EZTAB ", which read as three fillers — a settled product looking like it kept changing.

## Domain Rules — Bucket Fill Target (packing bench)

Added 2026-08-25, on its own route `/bucket-fill` (`components/BucketFillPage.tsx` -> `BucketFillCalculator`), reached from the **Post press** sidebar section.

- **Bucket fill and scale verification are separate pages on purpose**, despite being the same operator at the same scale minutes apart. They sit at opposite ends of the process: scale verification checks *dispensed ingredient* weights before pressing, bucket fill runs on *finished tablets* after. They were briefly built as two tabs on one page (2026-08-25, same day); that was split back out because a "Post press" nav section can't honestly hold a dispensing-stage check. Don't re-merge them.
- **"Post press" is a section, not a single nav button**, because yield/count reconciliation and packaging are expected to land there next — bucket fill is just the first entry.
- **`components/BenchShell.tsx` wraps the phone-first bench pages** (`/scale-verify`, `/scale-verify/review`, `/bucket-fill`) in the normal app shell so they're reachable from the sidebar instead of by typed URL only. Its `.app-bench` class scopes the app's **only** `@media` breakpoint (hide the nav rail below 768px) to these three pages — a 196px rail on a 375px phone costs more than it gives, but the rest of the app has no responsive rules at all and this is deliberately not the change that gives it some.

- **`lib/bucketFill.ts` is deliberately NOT part of the calc engine.** `target_scale_weight = bucket_weight + (tablet_count x tablet_unit_weight)` is packing-bench arithmetic: nothing feeds `calculateFreshBatch`/`calculateRegrind`, no blend math depends on it, and no row is written anywhere. Don't "consolidate" it into `lib/calc-engine/`.
- **The calculation returns full precision; rounding to 2 dp is display-only** (`fmt(n, 2)`), so a rounded figure never compounds. A test pins the unrounded float.
- **Tablet unit weight auto-populates from a saved Run (`run.result.targetWeightG`) or a `SavedFormulation` (`tabletWeightG`), and is always overridable** — there is no global "active formulation" concept in this app, so the operator picks the source. Reading from `run.result`, not `run.inputs`, is deliberate: `targetWeightG` is a typed number on both `FreshResult` and `RegrindResult`, where `inputs` is an untyped string bag. Any keystroke in the field resets the source to `'manual'` — a typed figure always wins over a pulled one.
- **Sanity-check bounds (`TYPICAL_MIN_BUCKET_TABLETS` 100 / `TYPICAL_MAX_BUCKET_TABLETS` 200,000 / `TYPICAL_MAX_BUCKET_LOAD_G` 30,000) are placeholders**, exactly like `DEFAULT_TOLERANCE_PERCENT` in `lib/scaleVerification.ts`: shaped like real limits, never checked against how anyone actually fills a bucket. They catch a fat-fingered extra zero, nothing more. They **warn and never block** — the target still renders alongside the warning. Only `validateBucketFill` (non-positive / non-integer / NaN) blocks.
- **`BucketPreset` is list/create/delete only, by design** — same shape as `RegrindLotPreset`, no PATCH. A bucket's tare doesn't drift; a wrong one is deleted and re-saved rather than silently rewritten under fills already computed against it. `/api/bucket-presets` (GET, POST), `/api/bucket-presets/[id]` (DELETE).
- **The "remaining to target" photo-verify readout is NOT built.** Wiring it needs an untared reading path through `ScaleVerification`, whose `expectedWeightG` is hard-wired to a run ingredient via `lib/runIngredientBreakdown.ts` — a schema/API decision, not an addition. Deferred deliberately, not overlooked.

## Blend Rationale Panel (the "Why" tab)

Added 2026-09-17 on the New run page, alongside Output/Variances/SOP.

- **`buildBlendRationale` (`lib/knownExcipients.ts`) is pure and tested**, like `lib/gmp.ts`. It takes the blend as name + % of blend and returns per-excipient assessments, role gaps and unrecognised names. `FormulateApp` builds its input from the **same merged figures the Output rows use** (grams / `totalBlendG`, filler merged with a same-named excipient), so the panel can never quote a percentage the amounts above it disagree with.
- **Every verdict is advisory.** `'above-typical'` means "outside the range this table knows", never "wrong" — real formulations sit outside typical ranges for reasons the app cannot see, and a tool that cries wrong about a good formulation teaches operators to ignore it. Same reason gaps are silent whenever any excipient is unrecognised: the unknown material may be the very lubricant it would claim is missing.
- **Regrind needs two pieces of context or it lies.** The lubricant is a `freshTopUp` (verdict `'top-up'`, explained rather than assessed — otherwise a correct 0.15% reads "below typical"), and the disintegrant/lubricant already in the reground powder are passed as `rolesCarriedIn` so they are not reported missing. Both are pinned by tests.
- **Ingredients at 0% are dropped**, same reasoning as the SOP: explaining the purpose of something nobody is weighing reads as an instruction to add it.
- **The printed batch sheet carries the rationale too**, as a "Why this blend" section after the SOP, at 8.5pt against the sheet's 12pt body — supporting explanation for whoever reads the sheet later, never a working instruction, so it must not compete with the weigh table or the SOP steps. The panel's on-screen caveat line is deliberately NOT printed (operator asked for it gone, 2026-09-17): the sheet goes to people who already know these are reference figures, and the per-item wording carries the hedging anyway. Reference-table content only: the AI tier is per-panel state and advisory, so it is deliberately not printed.
- **The AI tier (`/api/excipient-rationale`, `lib/excipientRationale.ts`) is opt-in per material** — a button, never automatic, so the panel costs nothing and always works offline. The prompt demands `null` over a guessed range and an `uncertain` flag, and a missing flag parses as uncertain; its output is labelled as AI-suggested, not reference-table fact. Same two-tier split as `knownActives`/`activeSuggestion`.

## AI Verification Layer — Integrity Rules

- AI math verification must never perform arithmetic in free-form token generation. It must go through a genuine tool-use round-trip: TypeScript computes the actual numbers server-side, feeds results back to the model, and only then can the model conclude "confirmed" or "discrepancy."
- There is an integrity gate that rejects any AI response containing a reported number that doesn't trace back to an actual tool output. Don't loosen or bypass this gate for convenience.
- Verification UX is two-tier: sub-threshold floating-point noise auto-confirms; real discrepancies require explicit human "Reviewed, proceeding" acknowledgment, logged to an audit trail, with save blocked until acknowledged.

## Working Style / Process

- Commit after each verified milestone, not in large batches — e.g. engine move, UI wiring, persistence layer, each Phase 4 sub-piece (verification round-trip, integrity gate) as separate commits.
